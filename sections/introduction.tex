Recent studies on AI coding agents have proven the efficacy of using Large Language Models (LLMs) to handle coding tasks such as code generation and debugging. To apply LLMs in daily software engineering scenarios, both industry and academia have proposed many agentic frameworks. Industry-proprietary examples include Google's Colab AI \cite{google_2025_colab_ai_first}, Claude Code \cite{anthropic_2025_claude_code_ga}, and Cursor Agent \cite{cursor_2025_agent_cli}. There is a continuous and rapid growth of user bases for these frameworks, reflecting their perceived utility in real-world software engineering tasks. Besides the proprietary frameworks, there are also many open-source implementations from both academia and industry, including Gemini Cli \cite{mullen_salva_2025_gemini_cli}, SWE-Agent \cite{yang2024sweagent}, AutoCodeRover \cite{zhang2024autocoderover}, and Agentless \cite{xia2024agentlessdemystifyingllmbasedsoftware}. These frameworks enable existing LLMs to achieve high task success rates when prompted with clear instructions and sufficient code context.

A common characteristic of these agents is that they issue many requests to the LLM during a single task. Each request often carries a long prompt: repository structure information, multiple code snippets retrieved as context, system instructions, and the issue description. The repeated and overlapping nature of this content across requests within a code repository means a serving system that re-processes every prompt from scratch wastes a large fraction of compute on tokens it has already seen. This redundancy directly translates to high time-to-first-token (TTFT) and high cumulative cost per task. The latency cost is particularly important because agentic workflows are interactive: a user typically waits for the agent's output, and slow generation degrades developer productivity in a way that aggregates across many sessions.

The standard solution to this redundancy is KV cache reuse, where the serving engine stores intermediate attention states from previous requests and reuses them when the same tokens appear again. Modern serving engines such as vLLM \cite{kwon2023vllm} and SGLang \cite{zheng2024sglangefficientexecutionstructured} implement prefix caching, which reuses cached KV states only when prompts share an exact prefix from the start. Throughout this thesis we refer to the LLM serving system, vLLM together with its KV cache layer, as the \emph{backend}, and to the context retrieval system that assembles the prompts as the \emph{frontend}. In an agentic setting, calls often share partial contexts that appear after some unique tokens, leading to low cache hit rates under prefix-only matching \cite{kwon2023vllm, zheng2024sglangefficientexecutionstructured}. CacheBlend \cite{yao2025cacheblendfastlargelanguage} addresses this by enabling \emph{position-independent} KV cache reuse: the prompt is treated as a sequence of chunks, each chunk is matched against the cache independently, and a small subset of cross-attention-sensitive tokens are recomputed to restore correctness. The original CacheBlend paper demonstrates 2--3$\times$ TTFT reduction and 3--5$\times$ throughput improvement on multi-round \textit{question-answering workloads}.

CacheBlend's original evaluations, however, used question-answering workloads, in which shared documents come first and the question comes last. Coding agents produce a different kind of traffic. An agent's prompt usually puts request-specific content, such as the issue being fixed, ahead of the repository context it shares with other requests. The agent often samples several candidate answers to the same prompt in parallel. And a single prompt can be long enough that the serving engine processes it over several scheduling steps. Whether position-independent reuse pays off under this traffic, and for which requests, has not been studied. This thesis is a case study of that question: we serve a real coding agent with LMCache, the reference implementation of CacheBlend, and measure what blending buys over prefix caching on the requests the agent actually sends.

This thesis makes two contributions:

\begin{itemize}
    \item \textbf{An end-to-end deployment}: a repository-aware coding agent served by vLLM with LMCache's implementation of CacheBlend, together with a recording and replay path that serves the same agent trace under different cache configurations and cache sizes.
    \item \textbf{A case study of cache behavior on a real agent trace}: we measure where the trace's reuse comes from, how it changes with cache size, and what a reused chunk is worth in latency, comparing CacheBlend against prefix caching, and close with a case study of when to use each.
\end{itemize}

To study cache reuse under realistic agentic traffic, the system is wrapped in an end-to-end pipeline that includes a context retrieval frontend. Producing a realistic agentic workload requires a method for assembling the per-request prompts that a real code agent would issue, including repository structure, relevant code snippets, and an issue description. We use RepoGraph \cite{ouyang2025repographenhancingaisoftware} combined with the Agentless procedural framework \cite{xia2024agentlessdemystifyingllmbasedsoftware} as a concrete instantiation of the frontend. The frontend is treated as a pluggable component: any context retrieval module that produces structured prompts with explicit chunk boundaries can be substituted for it without affecting the backend design. Our frontend evaluation shows that the integrated agent performs consistently across multiple LLM backends.

Our case study shows that blending's benefit on this agent is real but narrow. Most of the trace's reuse comes from exact repeats: the agent's sampled repair step re-sends the prompt of the request just before it, which accounts for 14.7\% of all prompt tokens and is captured by prefix caching and blending alike. Blending adds up to 3.9 percentage points on top, all of it in the localization stage, where requests for different issues share repository context that follows their own issue text. A request that blending hits runs a median of 4.3$\times$ faster than under prefix caching, and the speedup levels off at a ceiling set by the fraction of tokens blending recomputes. Cache size changes how many requests hit, not what a hit is worth: blending's hits are reused long after they are stored, so they are the first to be evicted as the cache shrinks, and a request that loses its hit falls back to prefix-caching speed. Applied to every request, blending is no faster than prefix caching, because it also recomputes part of every exact repeat. Sending exact repeats to prefix caching and all other requests to blending is faster than either alone and close to choosing the better mechanism for each request.

The remainder of this thesis is organized as follows. Chapter~\ref{cha:background} provides background on KV cache reuse and CacheBlend, then on context retrieval and RepoGraph, and motivates the case study. Chapter~\ref{cha:design} describes the system we study, from the agent frontend to the cache. Chapter~\ref{cha:eval} presents the case study: where the trace's reuse comes from, how it depends on cache size, what a reused chunk is worth, and when to blend rather than use prefix caching, followed by an accuracy evaluation of the agent frontend across multiple LLM backends.
