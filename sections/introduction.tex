Recent studies on AI coding agents have proven the efficacy of using Large Language Models (LLMs) to handle coding tasks such as code generation and debugging. To apply LLMs in daily software engineering scenarios, both industry and academia have proposed many agentic frameworks. Industry-proprietary examples include Google's Colab AI \cite{google_2025_colab_ai_first}, Claude Code \cite{anthropic_2025_claude_code_ga}, and Cursor Agent \cite{cursor_2025_agent_cli}. There is a continuous and rapid growth of user bases for these frameworks, reflecting their perceived utility in real-world software engineering tasks. Besides the proprietary frameworks, there are also many open-source implementations from both academia and industry, including Gemini Cli \cite{mullen_salva_2025_gemini_cli}, SWE-Agent \cite{yang2024sweagent}, AutoCodeRover \cite{zhang2024autocoderover}, and Agentless \cite{xia2024agentlessdemystifyingllmbasedsoftware}. These frameworks enable existing LLMs to achieve high task success rates when prompted with clear instructions and sufficient code context.

A common characteristic of these agents is that they issue many requests to the LLM during a single task. Each request often carries a long prompt: repository structure information, multiple code snippets retrieved as context, system instructions, and the issue description. Since requests on the same repository repeat much of this content, a serving system that processes every prompt from scratch spends a large fraction of its compute on tokens it has already seen. This leads to a high time-to-first-token (TTFT) and a high cost per task. Latency matters in particular because agentic workflows are interactive: the user usually waits for the agent's output, and slow responses add up over many sessions and hurt developer productivity.

The standard solution to this redundancy is KV cache reuse, where the serving engine stores intermediate attention states from previous requests and reuses them when the same tokens appear again. Modern serving engines such as vLLM \cite{kwon2023vllm} and SGLang \cite{zheng2024sglangefficientexecutionstructured} implement prefix caching, which reuses cached KV states only when prompts share an exact prefix from the start. Throughout this thesis we refer to the LLM serving system, vLLM together with its KV cache layer, as the \emph{backend}, and to the context retrieval system that assembles the prompts as the \emph{frontend}. In an agentic setting, calls often share partial contexts that appear after some unique tokens, leading to low cache hit rates under prefix-only matching \cite{kwon2023vllm, zheng2024sglangefficientexecutionstructured}. CacheBlend \cite{yao2025cacheblendfastlargelanguage} addresses this by enabling \emph{position-independent} KV cache reuse: the prompt is treated as a sequence of chunks, each chunk is matched against the cache independently, and a small subset of cross-attention-sensitive tokens are recomputed to restore correctness. The original CacheBlend paper demonstrates 2--3$\times$ TTFT reduction and 3--5$\times$ throughput improvement on multi-round \textit{question-answering workloads}.

However, CacheBlend was originally evaluated on question-answering workloads, where the shared documents are placed at the beginning of the prompt and the question at the end. Traffic from coding agents looks quite different. First, an agent's prompt usually places request-specific content, such as the issue being fixed, before the repository context that it shares with other requests. Second, the agent often samples several candidate answers from the same prompt in parallel. Third, a single prompt can be long enough that the serving engine needs several scheduling steps to process it. It is not clear whether position-independent reuse still pays off under this kind of traffic, or for which requests it does. In this thesis, we answer this question through a case study: we serve a real coding agent with LMCache, the reference implementation of CacheBlend, and compare blending with prefix caching on the requests that the agent actually sends.

The contributions of this thesis are as follows:

\begin{itemize}
    \item \textbf{End-to-end deployment.} We deploy a repository-aware coding agent on vLLM with LMCache's implementation of CacheBlend. We also add a record-and-replay path that lets us serve the same agent trace under different cache configurations and cache sizes.
    \item \textbf{Case study of cache behavior on a real agent trace.} Using this trace, we compare CacheBlend with prefix caching. We identify which requests benefit from each mechanism, how the benefit changes with cache size, and how much latency a reused chunk saves. Based on these results, we discuss when each mechanism should be used.
\end{itemize}

To get realistic agentic traffic, we need prompts that look like the ones a real coding agent would send, with repository structure, relevant code snippets and an issue description. We therefore build an end-to-end pipeline that includes a context retrieval frontend. For the frontend, we use RepoGraph \cite{ouyang2025repographenhancingaisoftware} together with the Agentless procedural framework \cite{xia2024agentlessdemystifyingllmbasedsoftware}. The frontend is a pluggable component: it can be replaced by any other context retrieval module that produces structured prompts with explicit chunk boundaries, without changing the backend. In our frontend evaluation, the integrated agent reaches comparable resolve rates across several LLM backends.

Our case study shows that blending does help this agent, but only for a small part of its requests. Most of the reuse in the trace comes from exact repeats. The agent's sampled repair step re-sends the prompt of the request right before it, and these repeats account for 14.7\% of all prompt tokens. Prefix caching and blending both capture them. Blending reuses up to 3.9 percentage points more on top of this, all of it in the localization stage, where requests for different issues share repository context that comes after their own issue text. When blending hits a request, the request runs a median of 4.3$\times$ faster than under prefix caching. This speedup stops growing at a ceiling that is determined by the fraction of tokens blending recomputes. As the cache shrinks, fewer requests hit, but each hit gives about the same speedup. Blending's hits are reused long after they are stored, so they are the first to be evicted, and a request that loses its hit simply runs at the same speed as under prefix caching. If every request is blended, blending is no faster than prefix caching overall, because it also recomputes part of every exact repeat. Sending exact repeats to prefix caching and all other requests to blending is faster than either mechanism alone, and comes close to choosing the better mechanism for each request.

The rest of this thesis is organized as follows. Chapter~\ref{cha:background} gives background on KV cache reuse and CacheBlend, as well as on context retrieval and RepoGraph, and motivates the case study. Chapter~\ref{cha:design} describes the system we study, from the agent frontend to the cache. Chapter~\ref{cha:eval} presents the case study and discusses when to use blending instead of prefix caching. It ends with an accuracy evaluation of the agent frontend across several LLM backends.
