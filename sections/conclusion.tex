\chapter{Conclusion}
\label{cha:conclusion}

In this thesis, we studied position-independent KV cache reuse for an LLM coding agent. We served a repository-aware coding agent with CacheBlend and with prefix caching, and replayed the requests it sends while working on SWE-bench issues at five different cache sizes. Our goal was to understand how much blending improves over prefix caching, which requests benefit from it, and how this depends on the cache size.

\section{Summary of Contributions}
\label{sec:conclusion_contributions}

Our first contribution is an end-to-end deployment. The RepoGraph + Agentless frontend generates realistic agentic prompts, an adapter module converts them into the format the backend cache engine expects, and vLLM with LMCache serves the requests with either CacheBlend or prefix caching. With request logging and replay, we can serve the same agent trace under each cache configuration and cache size, so the differences we measure come from the cache and not from changes in the agent's behavior.

Our second contribution is a case study of how the cache behaves on this trace. We measure which requests get cache hits under each mechanism, how this changes with cache size, and how much latency a reused chunk saves. We then use these results to decide when to use blending and when to use prefix caching.

\section{Summary of Findings}
\label{sec:conclusion_findings}

First, most of the agent's reuse comes from exact repeats. The sampled repair step re-sends the prompt of the request right before it. These repeats account for 14.7\% of all prompt tokens, and both prefix caching and blending capture them. Blending reuses up to 3.9 percentage points more, all in the localization stage, where prompts for different issues share repository context that comes after their own issue text. Whether a mechanism can reuse shared context therefore depends on where that context is placed in the prompt.

Second, blending's extra reuse is the part most affected by cache size. Exact repeats are reused by the next request, so they stay in the cache even when it is small. The shared localization context, in contrast, is reused long after it is stored, so it is evicted first. Blending loses part of its extra reuse at 1\% and 2\% of the working set, and keeps all of it from 5\% up.

Third, the speedup from a blended hit is limited by the recompute ratio. Blending recomputes every token that it could not reuse, and always at least a fixed fraction of the prompt. A request's speedup therefore increases with the fraction of the prompt that is reused, but levels off at about 4.4$\times$. This curve stays the same at every cache size. A smaller cache leads to fewer hits, but each hit gives about the same speedup, and a request that loses its hit runs at prefix-caching speed.

Fourth, when blending is used for every request, it is no faster than prefix caching on this trace, because it also recomputes part of every exact repeat, which prefix caching simply loads. Routing exact repeats to prefix caching and all other requests to blending is faster than either mechanism alone, and is within 0.4\% of choosing the better mechanism for each request.

Finally, our frontend evaluation showed that RepoGraph reaches comparable resolve rates with four LLM backends (GPT-4o, o4-mini, Claude 3.5 Sonnet, and Devstral Small), which supports the claim that it is portable across models.

\section{Future Work}
\label{sec:conclusion_future}

The routing result suggests that the same decision could be built into the serving engine itself. The engine could have a fast path that recognizes an exact repeat of a stored prompt and loads it without blending, so that it no longer needs a signal from the agent. More generally, the recompute ratio could be set per request instead of being fixed. An exact repeat does not need any recomputation, and the cost model in Section~\ref{sec:cb_worth} shows how much each extra point of recomputation costs a hit at a new position. The layout of the agent's prompts is another design choice worth exploring. Shared context placed before request-specific content can be reused by prefix caching, while shared context placed after it needs blending, so the agent's prompts and the cache could be designed together. Lastly, this thesis measured reuse and latency only. How blending affects the quality of the agent's outputs is left for future work.

On the frontend side, we kept the interface small on purpose. Replacing RepoGraph + Agentless with a more recent context retrieval module (for example, one based on agentic search instead of static graph queries) would give a useful point of comparison, and would test in practice whether the frontend is really pluggable.

Overall, our results show that position-independent reuse is useful in a coding agent's serving stack, but it should not be applied to every request by default. It helps requests whose shared context comes after new content, and each such hit gives a fixed speedup that is set by the recompute ratio. For exact repeats, which make up most of an agent's reuse, it only adds extra recomputation. Choosing the mechanism based on the type of reuse in each request gets the benefits of both.
