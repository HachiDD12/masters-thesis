\chapter{Conclusion}
\label{cha:conclusion}

This thesis studied position-independent KV cache reuse for an LLM coding agent. We served a repository-aware coding agent with CacheBlend and with prefix caching, replayed the requests it sends while working on SWE-bench issues at five cache sizes, and asked what blending buys over prefix caching, for which requests, and how that depends on the size of the cache.

\section{Summary of Contributions}
\label{sec:conclusion_contributions}

The first contribution is an end-to-end deployment in which the RepoGraph + Agentless frontend generates realistic agentic prompts, an adapter module bridges the frontend prompt format to the backend cache engine, and vLLM with LMCache serves the requests with either CacheBlend or prefix caching. A request logging and replay mechanism serves the same agent trace under each cache configuration and cache size, isolating the cache's effect from agent-side variability.

The second contribution is a case study of cache behavior on that trace. It measures where the reuse comes from, how it changes with cache size, and what a reused chunk is worth in latency, and uses the results to ask when to blend and when to use prefix caching.

\section{Summary of Findings}
\label{sec:conclusion_findings}

First, most of the agent's reuse is exact repetition. The agent's sampled repair step re-sends the prompt of the request just before it, which accounts for 14.7\% of all prompt tokens and is captured by prefix caching and blending alike. Blending adds up to 3.9 percentage points on top, all of it in the localization stage, where prompts for different issues share repository context that follows their own issue text. Where shared context sits in the prompt decides which mechanism can reuse it.

Second, blending's extra reuse is the most sensitive to cache size. Exact repeats are reused by the very next request and survive in a small cache, while the shared localization context is reused long after it is stored and is the first to be evicted. Blending keeps all of its extra reuse down to 5\% of the working set and loses part of it below that.

Third, the payoff of a blended hit is capped by the recompute ratio. Blending recomputes every token it could not reuse and at least a fixed fraction of the prompt, so a request's speedup grows with the share of the prompt it reuses and then levels off at about 4.4$\times$. The curve is the same at every cache size: a smaller cache means fewer hits, not cheaper ones, and a request that loses its hit falls back to prefix-caching speed.

Fourth, applied to every request, blending is no faster than prefix caching on this trace, because it also recomputes part of every exact repeat that prefix caching simply loads. Routing exact repeats to prefix caching and every other request to blending is faster than either mechanism alone and comes within 0.4\% of choosing the better mechanism for each request.

The frontend evaluation confirmed that RepoGraph produces comparable resolve rates across four LLM backends (GPT-4o, o4-mini, Claude 3.5 Sonnet, Devstral Small), which supports its portability claim.

\section{Future Work}
\label{sec:conclusion_future}

The routing result suggests building the same decision into the serving engine: a fast path that recognizes an exact repeat of a stored prompt and loads it without blending, so that the choice no longer depends on a signal from the agent. More generally, the recompute ratio could be chosen per request rather than fixed: an exact repeat needs no recomputation at all, and the payoff model of Section~\ref{sec:cb_worth} shows how much each point of recomputation costs a shifted hit. Agent prompt layout is a design lever in its own right. Shared context placed before request-specific content becomes reusable by prefix caching, while shared context placed after it needs blending, so the agent and the cache can be designed together. Finally, we measured reuse and latency; how blending affects the quality of the agent's outputs remains to be studied.

Beyond these, the frontend interface is intentionally narrow, and swapping RepoGraph + Agentless for a more recent context retrieval module (for example, one based on agentic search rather than static graph queries) would provide a useful comparison point and would validate the pluggable frontend claim in practice.

Taken together, the results show that position-independent reuse has a clear place in a coding agent's serving stack, but a narrower one than a blanket default. It pays off for requests whose shared context follows new content, it is worth a fixed amount per hit set by its recompute ratio, and it is wasted on the exact repeats that make up most of an agent's reuse. Choosing the mechanism by the kind of reuse a request carries keeps both benefits.
