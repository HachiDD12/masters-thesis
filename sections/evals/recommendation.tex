\section{Case Study: Blend or Prefix?}
\label{sec:recommendation}

The results above show that neither mechanism is the better choice for every request. For localization hits, blending is about four times faster than prefix caching. For exact repeats, however, prefix caching is faster. It simply loads the stored state of the earlier prompt, while blending still recomputes part of it, as it does for every hit, even though nothing in the prompt has moved. When every request uses the same mechanism, the two end up with the same overall latency: at 5\% of the working set, the mean TTFT over the whole trace is 2.10\,s under both mechanisms (Table~\ref{tab:routing}). This leads to a practical question: can we send each request to the mechanism that serves it best?

\subsection{Routing by Reuse Type}
\label{sec:rec_controller}

The two kinds of reuse are easy to tell apart before a request is served. An exact repeat sends a prompt that the cache has already seen in full. In our agent, every sampled repair request repeats the greedy repair prompt sent right before it, and the agent knows this when it sends the request. A router can therefore send exact repeats to prefix caching and all other requests to blending. This information does not have to come from the agent. The serving engine can also detect an exact repeat by comparing a hash of the whole prompt with the hashes of the prompts it has already stored.

Table~\ref{tab:routing} compares this routing policy with using a single mechanism for every request, at 2\% and 5\% of the working set. At both sizes, routing is faster than either mechanism on its own. It is 2.7\% faster than the better single mechanism at 2\% of the working set, and 3.3\% faster at 5\%. It is also within 0.4\% of the best possible per-request choice, where each request is served by whichever mechanism was faster for it. This means that a simple rule, which only needs to know whether a prompt is an exact repeat, gets almost all of the benefit of choosing the mechanism per request.

\subsection{Measured Routing}
\label{sec:rec_measured}

The routed results above are computed by combining per-request measurements from the separate prefix caching and blending runs. In an actual implementation of routing, both kinds of requests are served in the same run. A single cache then holds the KV state of both mechanisms, and their entries compete for the same space.
