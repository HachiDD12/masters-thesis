rather than a new caching mechanism. The idea is to split each prompt into chunks along context objects, where a context object is a code snippet with a symbol definition, a repository structure tree, or another self-contained piece of context. The caching itself is done by the backend. It looks up each chunk by its content, and when a chunk is reused at a different offset, it corrects the chunk's positional encoding. A cached chunk can therefore be reused wherever it appears in later prompts, which is what we call \emph{position-independent caching}.

To illustrate why the choice of chunk granularity matters, consider the following example. Suppose the agent constructs a prompt after context retrieval, consisting of four parts: system instructions, repository structure, issue description, and a block of relevant code snippets. A naive chunking strategy would treat this prompt as a single unit or divide it into four coarse blocks. With Cached Context, we further decompose the context blocks into finer-grained chunks. The relevant code snippets block, for example, might contain definitions for multiple symbols retrieved by RepoGraph, where each symbol definition is now its own cache chunk.

Now consider a subsequent prompt in the same workflow, but with slightly different localization and a partly different set of code snippets, while most symbols and other blocks remain the same. Under conventional prefix caching, the cache can be reused only when the overlapping content appears identically from the start of the prompt. With Cached Context paired with the backend's position-independent caching, each overlapping symbol definition is a cache hit regardless of where it appears in the new prompt. This is particularly valuable in agentic workflows, where the order and combination of context elements frequently varies across requests.

The layout of the prompt also matters. Since prefix caching only reuses content that matches from the start of the prompt, shared context at the beginning of the prompt can be reused by either mechanism. Shared context that comes after request-specific content, such as an issue description, can only be reused with position-independent caching. As we show in Section~\ref{sec:cb_where}, this second case is where blending's extra reuse comes from in our agent.

\subsection{Backend: API Server with CacheBlend}
\label{sec:design_arch_backend}

The backend consists of an API server that serves as the entry point for frontend requests. The server hosts the LLM inference engine (vLLM) with LMCache integration, which implements the CacheBlend algorithm for position-independent KV cache reuse. When a request arrives, the server performs the following steps:
\begin{enumerate}
    \item Parse the chat messages from the request.
    \item Pass the messages through the adapter module (described below) for tokenization and chunk extraction.
    \item Forward the processed prompt to the LLM engine with CacheBlend enabled.
    \item Return the generated response to the client.
\end{enumerate}

The backend provides a chat-completion interface that follows the OpenAI API format, so any frontend that uses this API can work with the backend. The only change the frontend needs is to mark the boundaries of context objects in its prompt templates. The cache reuses a chunk wherever it appears in a prompt. When the agent samples several answers from the same prompt, all samples share one blended copy of the cached state.

\subsection{Adapter Module}
\label{sec:design_adapter}

The adapter module connects the frontend prompt format to the backend cache engine. It is responsible for:
\begin{enumerate}
    \item \textbf{Chunk extraction}: identifying and retrieving individual context objects from the incoming chat messages.
    \item \textbf{Tokenization}: encoding each chunk using the model's tokenizer, including correct handling of models with custom tokenization schemes (e.g., Devstral).
    \item \textbf{Chunk stitching}: reassembling the tokenized chunks to produce the final prompt token sequence consumed by the LLM engine.
\end{enumerate}

The chunk granularity is set through the frontend prompt template. To chunk per symbol, the frontend adds a delimiter after each code snippet it fetches while exploring the code graph. For a coarser granularity (e.g., one chunk per context block), the delimiters are placed only between the major sections of the prompt. Chunks shorter than a configurable minimum length are merged with their neighbors. This lets the system adapt to different workloads and chunk sizes.

\subsection{Frontend: RepoGraph + Agentless}
\label{sec:design_arch_frontend}

We use RepoGraph as the frontend context retrieval algorithm, integrated with the Agentless procedural framework. Agentless follows a three-step routine:
\begin{enumerate}
    \item \textbf{Localize}: given an issue description, identify the files and code regions most likely to require modification.
    \item \textbf{Repair}: generate candidate patches for the localized regions.
    \item \textbf{Rerank}: evaluate and rank the candidate patches, selecting the most promising one for submission.
\end{enumerate}

RepoGraph enhances the localization phase by providing repository-aware context. Rather than relying solely on file-level search, Agentless can query RepoGraph's code graph to retrieve symbol definitions, call chains, and structural information. This gives the LLM more complete context. For example, when localizing a bug in a function, the model also receives definitions of the symbols referenced by that function.

To support Cached Context, we modify Agentless's prompt generation so that it marks the boundaries of context objects. This exposes the chunk boundaries to the backend adapter without changing what the prompt says. Apart from this change, the frontend is a pluggable component, and any retrieval module that marks chunk boundaries in its prompts can replace RepoGraph + Agentless without changes to the backend.

The agent sends three kinds of requests to the LLM during these steps. \emph{Localization} requests ask the model which files and code regions should be edited. \emph{Greedy repair} requests ask for a single candidate patch. Each greedy repair request is followed by a \emph{sampled repair} request, which sends the same prompt again and asks for several alternative patches in parallel. A sampled repair request is therefore an exact repeat of the request before it. Localization requests for different issues, on the other hand, share repository context but contain different issue text. Since the three types of requests behave very differently under caching, we analyze them separately in Chapter~\ref{cha:eval}.

\section{Measurement Infrastructure}
\label{sec:profiling}
\label{sec:request_logging}

To study cache behavior on agent traffic, we need to serve the same sequence of requests under different cache configurations, and to see what the cache engine does with each request. We built one subsystem for each of these two needs.

\paragraph{Per-request profiling.}
We add a per-request profiler along the critical path through the adapter, cache engine, storage backend, and GPU connector. The profiler records two kinds of intervals: \emph{operations}, which are logical units of work (e.g., the retrieve pass of a single request), and \emph{phases}, which split an operation into smaller timed steps (e.g., token database lookup, per-layer storage retrieval, per-layer GPU onload).

Each thread keeps its own operation stack in thread-local storage, so that timing records from different tensor-parallel workers do not get mixed up. For each phase, the profiler records its wall-clock duration, the ID of its parent operation, and the thread ID. When an operation finishes, the profiler writes a summary of it to a JSONL file, which we aggregate and plot afterwards.

\paragraph{Request logging and replay.}
For debugging and reproducible experiments, the API server also has a request logging module. During a server session, it saves all incoming requests and their responses to a local trace file.

With these traces, we can check which stage of the Agentless routine causes a performance bottleneck. For example, if localization prompts keep getting low cache hit rates, we can adjust the prompt template so that the context lines up better across requests.

The server can also \textbf{replay} a trace file: it parses the requests in the file and sends them to the engine again. Replay allows us to:
\begin{itemize}
    \item Evaluate on traces captured from a real agent without re-running the full agent pipeline.
    \item Test specific caching scenarios with small synthetic traces.
    \item Compare different cache configurations on exactly the same workload.
\end{itemize}

\paragraph{Cache configurations.}
The cache can run either with blending or as a standard prefix cache, and the size of the CPU cache that holds the KV state is set for each run. With replay, we can serve the same fixed trace under every combination of mechanism and cache size. This avoids the variation that would come from re-running the agent loop end to end. The case study in Chapter~\ref{cha:eval} is built on this setup.

\section{Frontend Integration Details}
\label{sec:design_frontend_impl}

We also made a few changes on the frontend side that make the system more reliable and make the prompts that reach the backend more realistic.

\subsection{Context Truncation}
\label{sec:context_truncation}

For complex coding tasks involving multiple files and nested dependencies, the frontend can exceed the model's token limit when constructing a prompt. Originally, prompts were simply cut off at the end once the token limit was reached. This often dropped important instructions (such as output format requirements or validation criteria) from the prompt. Even when the LLM gets enough context to understand the problem, it may still perform poorly because of the missing instructions.

Instead, we use the model's tokenizer to compute the token length of each context block and of the prompt template. Before building the prompt, we truncate the last context block so that it exactly fits the remaining token budget. The template and its instructions therefore always reach the LLM in full. This makes patch generation more reliable when the context is long.

\subsection{Local Store for Precomputed Data}
\label{sec:local_store}

Building the code graph and repository structure from scratch for every task instance takes a long time. To construct its graph, RepoGraph parses all source files with \texttt{tree-sitter}, finds symbol definitions and references, and builds the dependency graph. For large repositories, this can take several minutes.

We therefore added a local store that caches these data structures. The store is keyed by repository ID and commit hash, so the cached data stays valid for any task on the same version of the code. This helps the most when many issues come from the same repository, which is common in benchmarks such as SWE-bench, or when different agent sessions work on the same repository.
